# 角色与权限

## 业务需求

- 角色与权限控制后台业务模块的访问，不等同于用户登录或微软身份绑定。角色是一组授权，用户也可以获得直接授权；业务路由或代码必须检查权限，授予角色本身不会自动保护操作。
- `superadmin` 可以维护角色、权限目录及角色授权矩阵。具备 `users.edit` 的账号可以为普通用户分配角色，但非超级管理员只能分配自身已有权限覆盖的角色；管理 `admin` 账号或分配 `admin` 角色还需要 `users.manage-admins`。
- 角色或权限标识会被业务代码引用，创建后不能在管理页面重命名；更换标识需要创建新项。

## 实现设计

**角色与权限目录。** `superadmin` 可在“系统设置 → 角色与权限”中创建角色（标识由小写字母、数字和连字符组成），编辑显示名称与描述，或创建权限（`domain.ability` 两段式标识）并编辑描述。可用权限以目录和业务模块的授权检查为准，此处不维护另一份权限清单。后台功能、业务模块注册权限及页面新建权限时，超级管理员统一获得对应的 `domain.*` 授权，不逐项追加 `domain.ability`；同域后续新增能力也会被覆盖。其他角色需要显式授权；已有通配符授权覆盖新权限时，该角色也会获得对应权限。

**授权矩阵。** 非 `superadmin` 角色可勾选目录中的已有权限。取消勾选只针对目录内授权；若原有通配符仍覆盖被取消的权限，保存时提示冲突。目录外的原始授权不会被自动删除，也不作为可勾选权限显示。超级管理员的权限不能在页面中撤销。

**配置来源。** 角色、权限目录及授权矩阵持久化在 CodeIgniter Settings 中；`AuthGroups` 配置提供尚未保存时的默认值，已保存的整个目录或矩阵优先于配置。

**授权职责。** 路由过滤器负责入口认证和功能权限，业务代码负责目标对象、数据范围及业务条件的授权。所有 HTTP 入口已由相同权限的路由过滤器保护时，控制器不必重复检查该入口权限；目标账号保护、资源所有权及可见性等对象级授权仍须保留。用于页面展示、数据筛选和跳转选择的权限判断也不属于重复入口检查。菜单或按钮可见性不能替代服务端授权。

**功能自行定义权限。** 后台基础功能与业务模块遵循同一规则：所属代码声明并检查权限，通过自己的数据库迁移将权限加入 Settings 目录；角色页面集中展示和分配授权，不从菜单自动生成访问规则。后台功能按以下权限独立授权，角色页显示本地化功能分组，权限项直接使用权限标识及目录描述，不另设操作名称映射：

| 功能 | 权限 | 覆盖范围 |
| --- | --- | --- |
| 用户查看 | `users.view` | 用户列表、权限查看、导出及附件列表和下载 |
| 用户创建 | `users.create` | 创建普通用户、CSV 模板和导入 |
| 用户编辑 | `users.edit` | 编辑、角色分配、邀请、附件上传移除及微软绑定审批、拒绝、解绑 |
| 管理员管理 | `users.manage-admins` | 管理 `admin` 账号及其附件、微软绑定，或分配 `admin` 角色的附加权限；不能替代查看、创建和编辑权限 |
| 邮件发送设置 | `email-settings.manage` | 查看和修改发送设置、发送测试邮件 |
| 邮件记录 | `email-deliveries.view` | 查看和筛选发送记录 |
| 邮件模板 | `email-templates.manage` | 查看、编辑、重置模板 |
| 操作审计 | `operation-audit.view` | 查看和筛选审计记录 |
| 微软登录设置 | `microsoft-settings.manage` | 查看和修改登录配置；绑定管理仍需用户管理权限 |
| 角色与权限 | 固定为 `superadmin` 用户组 | 维护角色、目录和授权，不可通过普通角色权限委派 |

仪表盘和个人资料使用登录认证，不额外分配功能权限。管理员账号仅指属于 `admin` 角色的账号，`developer` 和自定义角色不因此被视为管理员。用户编辑和微软绑定管理共享目标账号的保护规则：非超级管理员不能管理角色授权或直接授权超出自身范围的账号，多角色账号不可通过这些入口管理。微软绑定管理位于微软设置页面，使用完整页面流程时需同时获得 `microsoft-settings.manage` 和 `users.edit`；绑定操作接口检查 `users.edit`，不授予配置修改能力。操作 `admin` 账号的绑定还需 `users.manage-admins`。已有 `superadmin` 的账号编辑和微软绑定保护规则不由该权限解除。

后台功能和业务模块的权限注册迁移只补充缺失目录项，保留已有描述和其他角色授权，并为超级管理员补齐域通配符；其合法单项授权按域归并并去重，目录外合法域授权也保留为域通配符。无法识别的授权原样保留，不据此生成新授权。其他角色需在角色页面显式授权。目录中的 `admin.settings`、`admin.access` 不替代上述功能权限；`users.delete` 当前没有对应的后台删除入口。页面访问和操作以上表及实际代码中的授权检查为准。

## 运行约束

后台功能或业务模块新增受保护操作时，在路由声明入口认证和功能权限，在业务代码落实所需的对象级授权，通过所属命名空间的迁移加入目录，再为需要访问的角色授权。保持自动路由关闭；新增路由或移除控制器的重复入口检查时，用 `php spark filter:check <方法> <路径>` 核对所有入口，并通过启用过滤器的 HTTP 测试验证未授权请求被拦截。部署执行 `php spark migrate --all`，即使目录已通过页面保存，迁移也会增量注册新权限；不能只修改配置默认值。页面手工创建的权限仍需代码实际使用才有效。新建角色后可在用户编辑页分配，但仅添加角色或权限不会自动改变现有用户的角色和会话状态。有关用户编辑和权限查看入口，参见[用户管理](user-management.md)。
